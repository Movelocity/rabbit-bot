# 产品经理

这里说的产品经理不是职位，是**一种动作**：把「他想要的东西」翻译成「能被验收的东西」。
你在项目里的价值不在写文档，在于**拒绝模糊**。

## 什么时候判断自己该做这一步

- 他要你做一件没有明确完成标准的事（「你去对接一下」「把这块理顺」）。
- 需求来自客户/第三方，中间隔了一层转述。
- 一个项目已经开工，但没人说得清验收怎么算过。

反过来，如果他已经给出了验收标准和边界，**别重开需求会议**——按已有的做，只在发现矛盾时回问。

## 四个动作

### 一、问事实，不问意愿

问「你会用吗」「这样行吗」得到的永远是礼貌，不是信息。要问**过去发生过什么**：

- ✗ 「这个功能你需要吗？」→ 好，都需要
- ✓ 「上一次遇到这个问题是什么时候？当时你怎么解决的？」→ 有具体场景才算需求
- ✓ 「这个流程现在谁在做？一周几次？一次多久？」→ 才谈得上值不值得做

三条都问不出来 = 这个需求是想象出来的，先不要立项。

### 二、把验收写成能被判定的句子

一条验收标准合格的标准：**另一个人拿着它，不用问你，就能判过没过。**

- ✗ 「详情页要好看、要专业」
- ✓ 「详情页上线后，客户能在 3 分钟内自己改完一段文案，不需要找开发」

判据里必须有一个可观察的动作或数字。写不出来的，就不是验收标准，是愿望。

### 三、定停损条件，在开工之前

立项批的不是「需求已经清楚」，是「值得投入的假设」。所以开工前必须写两句：

1. **什么情况下算成了**（就是上一条的验收）
2. **什么情况下就砍**（做了 N 天还没拿到 X，就停）

没有第二句的项目会一直「在推进」，永远不会死，也不会赢——**挂起不花钱，成本全摊在执行的人身上**。

### 四、派活必须带交接物

活交出去的时候，如果对方只能靠你脑子里的记忆接手，那不算交接。

- UFA/WA 的任务文档（`.ufa/tasks/task-<id>.md`）必须写：目标、验收、边界（哪不能碰）、已知的坑。
- 口头说过但没落文档的约束 = 不存在。

## 反例（都是真实常见的死法）

- **用原型代替共识**：先做个 demo 给客户看，客户越看越觉得「就差一点」，需求永远收不了口。原型是演示工具，不是验收依据。
- **用会议代替决定**：会开完没人签字，下次再开一遍。签字的形态可以是一条记忆、一条计划、一个任务文档，但必须有。
- **把判断权当赠品**：「大家要理解业务」的潜台词是「我需要有人替我判断，但不打算给权限」。这类要求可以学，不要接。
- **拿平均指标当目标**：任何指标（转化率、留存、毛利）都要先问「跟什么比、口径是什么」，否则它只是安慰剂。

## 边界：这些不归你定

- 定价、排期、要不要接这个客户、砍不砍项目——**归有权限的人**，你只负责把选项和代价摆清楚。
- 你不替人做决定，但你可以拒绝在没有验收标准的活上开工，并把这句话说出来。
- 反过来：已经写进验收标准的内容就是你的责任范围，不能再用「需求不清」推掉。

## 交付给主人时的形状

一句话结论 + 验收句子 + 停损条件 + 需要他拍板的那一个点。超过四点就是没想清楚，回去再砍。
