# 模板一 · Example Mapping

来源：Matt Wynne（Cucumber）。用途：**把一条说不清的需求，拆成能被测试的例子**。
花时：25 分钟。参加的人：提需求的人 + 干活的人，最多 4 个。

## 四张卡

| 颜色 | 是什么 | 写几条 |
|---|---|---|
| 黄 | Story：这次要谈的那**一条**需求，一句话 | 1 |
| 蓝 | Rule：这条需求背后的规则 | 3–6 |
| 绿 | Example：每条规则举一个**具体**例子 | 每条规则 ≥1 |
| 红 | Question：当场答不上来的问题 | 越少越好 |

## 填法

```
黄 · Story
  <一句话：谁 要 什么，为了 什么>

蓝 · Rule 1
  <一行规则>

 绿 · Example 1.1
    给定 <前置状态，具体到数字/名字>
    当    <发生什么动作>
    那么  <可观察的结果，具体到数字/文案/状态>

 绿 · Example 1.2
    ...

红 · Question
  <当场答不上来的、要问谁、什么时候问>
```

## 判定规则（硬）

- **红卡 > 2 张 → 不许开工。** 先答完问题再来。
- **绿卡必须能变成一条测试。** 写不成「给定/当/那么」的，是愿望不是例子。
- **蓝卡不许出现模糊词**（快、稳、好看、尽量、灵活）。听到就当场量化。
- 一条黄卡 25 分钟聊不完 = 这条需求太大了，先拆。

## 正例（电商广告报表）

```
黄：运营要能每天早上看出哪几个 ASIN 把预算花超了

蓝1：超预算的判定口径 = 当日花费 > 当日预算
  绿1：给定 活动 A 预算 100 元，当 当日花费 118 元，那么 该活动标红并显示「超 18%」
  绿2：给定 活动 B 预算 100 元，当 当日花费 100 元，那么 不标红（等于不算超）

蓝2：报表范围 = 过去 7 天，按活动×ASIN 两个维度
  绿3：给定 昨天有一个 ASIN 花了 30 元，当 打开报表，那么 它在「过去 7 天」里且金额 30.00

红：预算字段从后台取还是从我们库里算？→ 问 CTO，本周五前
红：时区按站点所在国还是北京时间？→ 问运营主管，本周三前
```

结论：这条需求红卡 2 张、绿卡 3 条，可以开工；验收直接用绿卡。

## 反例

- 绿卡写成「当用户点击时，系统响应迅速」——没法测，等于没写。
- 红卡全塞进「后续再确认」——那就是把不确定性推到交付前一天。
