# 模板三 · Shape Up 的 Pitch

来源：Basecamp《Shape Up》（basecamp.com/shapeup）。用途：**先定时间预算，再定范围**——专治「都做、都按时」。
花时：半天。产出：一页纸，能直接拿去拍板。

## 六段

```
1. Problem（现状哪疼，带数字）
2. Appetite（时间预算：这件事我最多给 N 周，是上限不是估计）
3. Solution（粗方案，画个流程或列 5 条，不做细设计）
4. Rabbit holes（要先挖掉的坑：已知的诱惑和陷阱）
5. No-gos（明确不做的事，写死）
6. Boundaries（谁能碰哪、要不要动线上数据、回滚怎么做）
```

## 关键在第二段

- **Appetite 是预算，不是估算。** 估算问「要多久」，预算说「只给这么久」。
- 小批次 1–2 周、大批次 4–6 周，不给中间档。
- 时间固定后，**范围自动成为变量**——这就是「需求砍不掉」的解：「这些在预算内，那些不在，要加就换出」。
- 说「尽量快」「看情况」的，不是预算，是没决定。

## 正例（同一件事）

```
1. Problem：上个月有 3 个活动超预算过夜才发现，合计多花 4,200 元；现在靠人工每天翻后台，一次 20 分钟
2. Appetite：2 周（含上线）。给不到 2 周就不做，宁可用人工盯
3. Solution：每天早上 7:50 抓一次后台 → 算出超支 → 按超支比例排序 → 发一条群消息（不建页面、不做权限）
4. Rabbit holes：后台没有 API（要浏览器抓，可能被风控）；时区口径不统一；两个店铺预算字段名不同
5. No-gos：不做历史趋势图、不做邮件推送、不做多语言、不接管调价动作
6. Boundaries：只读后台，不写任何数据；抓取失败就发「本次未取到」而不是静默；脚本可一键停
```

## 判定规则（硬）

- 没有 `Appetite` 或写成「尽快」→ 这份 pitch 不成立。
- 没有 `No-gos` → 范围会一路膨胀，等于没有预算。
- `Rabbit holes` 里有一条「可能做不成」但没写退路 → 先解决它，或把它写进 No-gos。
- 一页写不下就是还没想清，不是纸太小。

## 与例子的关系

Pitch 通过后，每条 Solution 拆成 Example Mapping 谈验收；No-gos 直接进交付时的「不做什么」清单。
