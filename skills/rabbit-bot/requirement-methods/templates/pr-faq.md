# 模板四 · PR-FAQ（Working Backwards）

来源：Amazon。用途：**一页纸判该不该立项**——写不出来就不该做。
花时：半天。产出：上半页新闻稿 + 下半页十条 FAQ。

## 上半页：新闻稿（假装已经上线了）

```
<产品名>，给<谁>用的<是什么>
——解决<什么疼>，现在<怎么做>

<城市/日期> —— <一段话：谁遇到了什么麻烦，以前怎么办，现在怎么办>

「<一句用户会亲口说的话，带具体数字或时间>」——<假设的用户，岗位>
（不要写 CEO 和公司愿景的引用，写用户的）

<怎么用：三步，每步一句>

<一句：凭什么我们能做，别人做不到>
```

## 下半页：FAQ（十条，一半是内部会反对的）

```
外部 FAQ
1. 客户第一句会问什么？（价格 / 数据从哪来 / 会不会动我的账号）
2. 不用它的替代方案是什么？为什么比它差？
3. 谁付钱、付多少？

内部 FAQ
4. 成本多少（人、时间、钱）？最贵的是哪一步？
5. 最容易做不出来的是哪一块？退路是什么？
6. 跟现有系统哪里冲突（数据、口径、权限）？
7. 上线后谁维护？他有没有时间？
8. 出事故怎么发现、怎么回滚？
9. 为什么现在做，不做会怎样？
10. 什么情况下我们主动砍掉它？
```

## 判定规则（硬）

- **写不出「用户会亲口说的那句话」→ 这个产品还不存在。** 那句话必须带数字或时间，不能是「很方便」。
- **第 10 条写不出来 → 不许立项。** 没有停损条件的项目会一直「在推进」。
- 第 4 条估不出成本量级（天/周/月）→ 说明还没摸过实现。
- 新闻稿出现「赋能」「一站式」「闭环」这类词 → 重写，换成动作。

## 正例（同一件事的新闻稿）

```
广告花费管家，给亚马逊运营用的超支报警
——不用每天翻后台，超预算的活动早上 8 点前自己送到你眼前

「以前 3 个活动超支过夜我才发现，多花了 4,200 块。现在早上开会前就知道该调哪一个。」

用法：连上店铺 → 设一个超支阈值 → 每天 7:50 收到一条清单

凭什么：我们自己就是运营，口径早就对齐过；市面上的工具都不认多店铺的预算字段差异。
```

## 反面（真实常见）

「XX 智能助手，赋能运营全流程，打通数据闭环」——没有用户、没有数字、没有停损，
这类文档唯一的作用是让项目看起来已经想清楚了。
