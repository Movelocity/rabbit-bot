# UFA / WA 双 Agent 架构

> 2026-11-01 定稿。参考 DeepSeek Harness《Super-agent 设计探索》，按 rabbit-bot 的场景做了简化。
> 这份是**行为约定**，不是实现说明。实现可以换，语义不能漂。

---

## 一、职责

| | UFA（user facing agent） | WA（working agent） |
|---|---|---|
| 人格 | 有，且是核心 | **无**，只有效率提示词 |
| 面向 | 人 | 任务 |
| 模型 | 强（判断 + 表达） | 强（执行） |
| 工具 | 文件读（单次 ≤500 字符）、文件写（无上限）、登记任务、查任务、查历史消息（支持 SQL） | 全量：shell（宿主或沙盒）、文件读写、网络搜索 |
| 不做什么 | **不直接干重活**（不做复杂文件读写） | **不直接跟人说话** |
| 输出 | 消息 | 面板状态 + 产物 |

**一句话**：UFA 保证「跟你聊天的是个人」，WA 保证「事情真的做完了」。

### 为什么不能合成一个

2026-09 斯坦福医学院在 Nature 上的一项研究提供了一个现成的类比：人脑不是单一器官，而是**两套神经系统**——前脑/中脑由 Otx2 祖细胞发育、后脑/脑干由 Gbx2 祖细胞发育——在数亿年里各自独立演化，最后被装进同一个颅骨。

**先划清边界**：生物上这两套不能分开活，脑干一停，前脑立刻报废。而 UFA/WA 是松耦合的，靠面板交接，比它松得多。所以这里借的不是「分工」，是**「高层是另起一套，不是升级出来的」**。

工程上的推论很直接：

- UFA 和 WA 应当**分别独立设计**，而不是把同一份提示词切成两半；
- 单 Agent 又聊天又干活，等于要求**一个器官同时管心跳和写诗**。觉得别扭，不是它能力不够，是结构上不该这么长。

## 二、消息流

### 2.1 触发

**只有用户发消息才触发 UFA 识别**。没有消息就不唤醒，不做定时轮询。

### 2.2 主流程

```
用户消息到达
  → 唤醒 UFA（每条都触发，不在代码层预判）
      ├ 判断「完整」→ 立刻接话
      └ 判断「不完整」→ 挂 30s 定时，窗口内消息只入队
  → 30s 到 → 唤醒一次，把窗口内全部消息一起看 → 接话
```

「完整」的判断归 UFA，不归代码。代码只负责计时。

### 2.3 边界（必须全覆盖）

| 情况 | 处理 |
|---|---|
| 30s 窗口内又来消息 | **只入队，不重开定时**（延迟读不递归） |
| 30s 到点同时有新消息 | 合并成一次读取，一次回复 |
| UFA 正在生成时来消息 | 先记账，生成完再处理，**不打断** |
| 面板同时有更新 | 走 tick 排队，等 UFA 这轮结束 |
| 窗口期内用户发「别等了」类信号 | 立即唤醒，不等到点 |
| 用户在窗口内连发图片/文档 | 全部入队，按到达顺序给 UFA |

### 2.4 时间观念

UFA 看到的每条消息**都带时间戳**。它必须知道「这条是三小时前发的」和「这条是刚发的」不是一回事。

## 三、待办面板

### 3.1 一条任务的字段（轻结构化）

```
目标       一句话，做什么
产出物     做完之后能看到/拿到什么
约束       不能碰什么、必须遵守什么
验收       怎么算做完
关联文件   需要读的路径
起止时间   开始时间可空（= 立即）；未来时间 = 定时任务
```

**不加更多字段**。字段多了 UFA 写不动，WA 也不会读。

### 3.2 状态是隐式的

**不写状态机，不写 `blocked → resumed` 的转换代码。**

- 进行中：面板上有这条，没有结论
- 卡住：WA 在上下文里写一句「卡在 X，需要用户确认 Y」
- 完成：写回产物 + 结论
- 失败：写回失败原因

**状态就是文字本身**。UFA 读到什么就是什么。

### 3.3 回传路径

```
WA 更新面板（状态 / 产物）
  → 非打断式唤醒 UFA（UFA 正在生成就等它生成完，再走 tick）
  → UFA 读面板，挑值得说的转述给用户
```

**用户答了 WA 的问题之后**：UFA 把回答**追加到同一条任务上下文**，WA 下次被唤醒时自己读，自己判断能不能继续。没有回调、没有恢复信号。

### 3.4 WA 的唤醒源

1. 面板上有新任务
2. 定时任务到点
3. 被取消（强制打断）

## 四、记忆

### 4.1 时间维度

```sql
valid_from    INTEGER   -- NULL 视为 created_at
valid_to      INTEGER   -- NULL = 至今有效
superseded_by INTEGER   -- 指向顶掉它的那条
```

`kind` 沿用现有 `fact` / `topic`，新增 `plan`（计划型，带到期时间，自己失效）。

### 4.2 检索

- 当前有效：`WHERE valid_to IS NULL`
- 某时刻有效：`WHERE valid_from <= ? AND (valid_to IS NULL OR valid_to > ?)`

### 4.3 谁判冲突

**写入的人自己说**，不自动推断。

UFA 写记忆时必须回答两个问题：

1. 这条从什么时候开始成立？
2. 它顶掉了之前的哪条？

**答不上来就不写。**

先只加字段，不做自动 supersede。等真出现「两条打架」的例子再补。

### 4.4 写入时机（只有两个）

1. **用户明确纠正，或给出新事实**
2. **话题结束 / 用户下线**

平时不写。省得把闲话塞进库里。

### 4.5 跨池

`user_id` 是隔离边界，`source_pool_id` 只是出处、不参与检索。**现有表结构已经支持，不需改。**

## 五、取消与中断

**取消 ≠ 杀进程。**

- 取消信号 = 设一个检查点标记
- WA 在**当前工具调用结束后**停止，不硬杀
- 停下时把「做到哪了、什么状态下停的、有没有半成品」写回面板

理由：正在写文件 / 正在 `git push` 的时候硬杀，会留下人看不懂的半成品，比不取消更麻烦。

## 六、上下文

### 6.1 自动总结

UFA 和 WA 都有 token 阈值自动总结，**直接用 pi 框架已有的机制**，不自己写。

### 6.2 文件系统

UFA 的沙盒和 WA 的 shell **是同一个文件系统**。UFA 写的任务描述，WA 必须能直接读到。

### 6.3 日志

WA 的执行日志进 `jsonl`，供后续复盘。

## 七、砍掉的旧机制

| 机制 | 处置 | 原因 |
|---|---|---|
| `tide` 唤醒 | **砍** | 触发源是定时器，不是「有事」 |
| `energy` 充能（`E` + `I(E)`） | **砍** | 度量的是「回复及时率」，是手段不是目的 |
| `tide_events` 表 | **砍** | 跟着一起删 |
| `wave` 水位 | 已关 | 早就是回退开关 |

**主动机制重新设计，暂不定。** 等 UFA 跑起来、看清它真实的活跃节奏再定——现在就定等于猜。
