# 充能模型（energy）：红蓝染色 → 分档充能 → 退火冷却

> **状态：推演阶段，未接进 wake。** 下面所有数字都是 `app/scripts/sim-energy.ts` 跑出来的，
> 改常量再跑一遍就能复现。接进项目之前先看这份结论，别直接改 `wave.ts`。

## 1. 要解决的问题

现在的额度是**死的**：`maxWakesPerDay=8` 固定，`maxStages=3` 固定，跟关系状态无关。
你热聊一整天她还是 8 次；你消失三天她还是 8 次。

10-29 下午的真实事故说明了「死额度」能死到什么程度：

```
她连着 3 次放行都选择不说（tide_events 里全是「没发」）
→ 水位退到第 4 档，stage > maxStages 直接判死
→ 四小时一次都没被叫醒，直到有新消息把水位重新推高
```

**用「不主动」惩罚「不主动」。** 当天已改成「没发不消耗档位」（`a670a73`），但那是止血；
真正要换的是「额度从哪来」。

## 2. 红蓝染色：只统计红→蓝的区间

```
🔴 红 = 她说的话（不管主动开口还是回答）
🔵 蓝 = 主人说的话
```

**只有「红在前、蓝在后」的相邻区间计分。** 蓝→红（他先说她后答）不计分——
这条规则天然排除了「他找她、她回」的情况，不需要额外判断谁先开口。

**连发多条只算一个区间**：区间 = 最后一个红 → 第一个蓝。否则她连发三条就能拿三次充能。

真实例子（2026-10-29）：

```
🔴 18:57:32  她连发 4 条
🔵 19:37:00  主人回（在说这套机制）
区间 39 分钟 → 落在「60 分钟」档 → 得分 0.30 → 充能 +0.15
```

## 3. 三个动作跟成本

| 动作 | 触发 | 成本 | 理由 |
|---|---|---|---|
| **回答** | `tick: 有未读`——醒来发现对话记录 | **−0.1** | 谁回答问题不耗能呢 |
| **插话 / 起话头** | tick 带着「引导话题、别让对话变无聊」的任务 | **−1.0** | 这才是真正的主动开口 |
| **充能** | 他回了她的话（红→蓝区间成形） | **+0.5 × 档位** | 档位见下 |

**关键：energy 管的是「打扰的额度」，不是「说话的额度」。** 你说了话她接话，不该花掉一次主动机会——
所以回答只要 0.1。这条是推演 v1 救命的一刀：v1 里所有说话都扣 1，结果**热聊 8 轮她就被拦了 2 次**，
聊天越热额度越少，跟预期完全反了。

## 4. 分档（区间长度 → 得分）

| 档 | 回复用时 | 得分 |
|---|---|---|
| 1 | ≤1 分钟 | **1.00** |
| 2 | ≤5 分钟 | 0.85 |
| 3 | ≤10 分钟 | 0.70 |
| 4 | ≤20 分钟 | 0.55 |
| 5 | ≤30 分钟 | 0.45 |
| 6 | ≤60 分钟 | 0.30 |
| 7 | ≤120 分钟 | 0.20 |
| 8 | ≤12 小时 | 0.10 |
| 9 | ≤24 小时 | 0.03 |
| — | >24 小时 | **0，且算进分母** |

递减比档位密：1 分钟拖到 5 分钟和 2 小时拖到 12 小时，意义差得远。

## 5. 隔夜结算：今天的基准

凌晨算昨天的：

```
分母 = 她昨天发出的条数（还没满 24h 的不计，留到明天）
p    = Σ 每条对应得分 / 分母
c    = min(1, 分母 / 3)        # 样本太少打折
E_基准 = clamp(round(1 + 7 × p × c), 1, 8)
```

`c` 是必需品：不然「她只发 1 条、1分钟被回」直接算满分 8 次，太便宜。

实测：

| 昨天 | E |
|---|---|
| 8 个区间全 1 分钟内回 | 8 |
| 10 个：8 个 10 分钟、2 个没回 | 5 |
| 6 个：2 个 5 分钟、4 个没回 | 3 |
| 20 个全部 30 分钟 | 4 |
| 20 个全部 2 小时 | 2 |
| 只有 1 个区间、1 分钟 | 3 |
| 2 个都没回 | 1 |

## 6. 冷却：退火式，且睡觉不掉电

```
E(t→t') = 1 + (E − 1) · 0.5^(活跃分钟 / 半衰期)
```

两条设计：

- **趋向 1 不是 0**：0 意味着机制停摆，又回到「四小时没醒」那个坑。1 是「每天至少一次」的保底。
- **只算活跃时段（08:00–24:00）**：睡觉时她不在线，电量不该往下掉。这条是推演里发现的真 bug——
  v2 从 0 点开始算，`E_基准=3` 在没人说话的 9 小时里就冷没了，早上起床只剩 1 点，这天等于没有额度。

**冷却地板 1，但消耗可以跌破 1。** 用掉最后一次主动后 E=0，当天不能再主动；第二天结算重置。

## 7. 实验结果

参数：半衰 8h、回答 −0.1、主动 −1.0、充能 +0.5×档位、上限恒定 8、地板 1。

```
A 早聊 40 分钟冲到 6.25，之后整天没人
   08:3.0 10:6.0 12:5.2 14:4.5 16:3.9 18:3.5 20:3.1 22:2.8 24:2.5

B 全天稀疏 4 轮（每轮 5 分钟内回）→ 主动 3 次、被拦 1 次
   08:3.0 09:1.8 12:2.0 15:1.3 18:1.2 21:0.6 24:0.6

C 一整天没互动（从 5 开始）→ 24:00 还有 2.0，明早仍能主动一次
   08:5.0 12:3.8 16:3.0 20:2.4 24:2.0

D 早聊到 5.64，20:00 主动一次后剩 1.8
   10:5.3 14:4.1 18:3.2 20:1.8 24:1.6

E 一天没回（基准 1，主动 4 次）→ 只发出 1 次，被拦 3 次
```

**半衰期取哪个值**（09:00 充到 8，之后不管它）：

| 半衰 | 12:00 | 15:00 | 18:00 | 21:00 | 24:00 |
|---|---|---|---|---|---|
| 4h | 5.2 | 3.5 | 2.5 | 1.9 | 1.5 |
| **8h** | 6.4 | 5.2 | 4.2 | 3.5 | 2.9 |
| 12h | 6.9 | 5.9 | 5.2 | 4.5 | 3.9 |
| 24h | 7.4 | 6.9 | 6.4 | 5.9 | 5.5 |

推荐 **8h**：早上聊热、下午有余温、晚上还能说一句、半夜掉到底。4h 太急（下午就没电），
12h/24h 基本等于不衰减，退火白加。

**行为分布**（这才是这套机制真正改变的东西）：

| 关系状态 | 隔夜 E | 一天实际主动 |
|---|---|---|
| 昨天全秒回 | 8 | 6~7 次 |
| 正常（回复 5~30 分钟） | 3~5 | 3~4 次 |
| 一天没回 | 1 | **1 次，用掉就没了** |
| 冷场三天 | 1 | 1 次/天，直到他回来说话 |

## 8. 怎么复现

```bash
cd ~/projects/rabbit-bot/app
npx tsx scripts/sim-energy.ts
```

改参数就改脚本顶部那 8 个常量（`COST_ANSWER`/`COST_INIT`/`GAIN`/`FLOOR`/`CAP`/`HALF_H`/
`ACTIVE_START`/`ACTIVE_END`），然后加自己的场景：`sim("名字", 基准E, [{t: 分钟, color:"r", kind:"init"}])`。

`color`：`r` 她说、`b` 他说；`kind`：`init` 主动开口 / `answer` 回答（蓝的 kind 忽略）。

## 9. 还没定的

- **半衰期 8h 还是 12h**——8h 是我推荐的，看你要不要更温和
- **插话返还 0.5 还是 1.0**——现在插话是净亏 0.5（连续插 4 次就到底），如果你觉得热聊时该撑得住，就把「他回应她的主动」的返还算满
- **E 存哪**：`kv` 表够用（`energy:当前值` + `energy:base:日期`），还是单开一张表记每日结算？单开表能查历史，但多一份 schema
- **结算时刻**：0 点还是早上 8 点？按「活跃时段」的说法，8 点更合理
- **和 `maxStages` 的关系**：应该**替代**，不是叠加。两套上限同时活着就是互相打架（10-29 就是这么死的）

## 10. 推演过程踩的坑

记在这里，免得接进项目时重犯：

1. **v1：所有说话都扣 1** → 热聊 8 轮被拦 2 次，越聊越没额度。救法：拆成「回答 0.1 / 主动 1.0」。
2. **v2：冷却从 0 点算** → 睡一觉 8 小时，`E_base=3` 冷到 1.06，早上等于没额度。救法：只算活跃时段。
3. **v3：把地板设成 0**（为了救「一直被拦」的场景）→ `E_base=1` 冷却一小时掉到 0.93，**一次主动都发不出**，
   下限 1 直接失效。救法：地板回到 1，但消耗允许跌破 1。
4. **显示 bug**：小时曲线取「最后一个事件时的快照」，没继续冷却 → 10:00–17:00 显示恒定值。救法：查表时补算到该时刻。
5. **时间区间传错**：把「相对差值」当「从 0 点起的绝对时间」传给活跃分钟计算 → 一律算出 0 分钟，冷却看起来完全没生效。
