# 记忆注入与可追溯：现状、问题、可选方向

> 状态：**已决策，代码已改**（2026-11-11）：不再主动注入记忆和别名，改为 agent 需要时用工具/脚本/CLI 按关键词查；下文「现状」保留为改动前的记录。
> 2026-11-11

## 零、决策（2026-11-11）

- **不主动注入**：唤醒 prompt 不再放记忆正文，也不再做别名「说法对照」。
- **按需检索**：agent 在指代不清、引用旧事、问关系/影响面、上下文矛盾时，自己用 `memory`（search/recent/trace）、`map`、`chat search` 查。提示词 `system.md` 第 13 条写死了触发条件。
- **不重复查**：靠提示词约束「上下文里已有结果的同一关键词不重查」；暂不做会话级查询台账。
- **保留**：`user_id` 仍随消息给出（否则无法按人查）；业务地图仍只在 system prompt 放一行索引。
- 风险：从「程序保证想得起来」变成「模型判断该查」，可能漏查。靠触发词、工具描述、loopguard 和后续日志观察缓解。

## 一、现状（改动前）

### 1. 唤醒时注入哪些人（`app/src/app.ts:861-880`）

- 只看本轮 `involved` 的池：有未读、计划到点、主动开口涉及的池。
- 人只取**本轮未读消息的发送者**：`unread.filter(pool_id=pid && user_id)`。
- 每个 `池|用户` **一个会话只注入一次**：命中 `engine.seenPools` 的 key 就跳过；交接/换新会话时 `seenPools.clear()`（`app/src/agent/engine.ts:318`）。
- 该用户没有有效记忆，就不出现记忆块。

### 2. 注入哪些条（`app/src/core/db.ts` `visibleMemories`）

- 只要当前有效：`valid_to IS NULL`，已过期、被 supersede 的都不给。
- scope 过滤：`all` 任意池；`pool` 只在来源池；`private` 只在私聊；`group` 只在群聊。
- 不按关键词、话题、时间相关度筛；`ORDER BY id DESC LIMIT maxMemoriesPerUser`。
- 上限 `context.maxMemoriesPerUser`，默认 **8**（`app/config/default.json:29`）。
- kind 全收（fact / plan / alias / topic）。

### 3. 注入成什么样（`app/src/agent/prompt.ts:75-80`）

```
记忆 <user_id>（在 <池别名> 可见；#号是条目 id，改口时用得上）：#12 内容；#15 内容
```

- 只有 `#id + content`：**不带 valid_from / valid_to，也不带来源 seq**。
- alias 除了进记忆块，还会被 `resolveAliases` 单独生成「说法对照」块。
- 另有「正在跟你说话的人：名字（user_id=…）」块，负责把 id 对到人。

### 4. 本轮已落地、与本文相关的改动

- 记忆写入时自动绑来源消息 seq 区间 `source_seq_start/end`，`memory action=trace` 可回看来源前后文（`app/src/ops/memories.ts`、`app/src/agent/tools.ts`）。
- 正文规则：群里、或被记的人不是当前说话人时，content 必须带名字（`app/prompts/system.md` 第 8 条）。
- 去掉了 `supersede / close / update / delete / trace` 的 `user` 一致性校验：记忆按 id 操作，`user` 不是权限边界。

## 二、问题

| # | 问题 | 影响 |
|---|---|---|
| M1 | **一个会话只注入一次** | 会话中后期新记的记忆、更新的状态不会自动出现在后续唤醒里，模型看到的是会话开头那批 |
| M2 | **纯主动开口不注入记忆** | `users` 来自 unread；无未读的 proactive tick 没有记忆块——而她主动找话时最需要记得对方 |
| M3 | **选择只看最新 8 条** | 按 id 倒序截断，旧的稳定事实（过敏、称呼、重要关系）会被新记的琐事挤出 |
| M4 | **无相关性 / 重要度** | 不按当前对话关键词、话题、置顶标记挑，纯时间序 |
| M5 | **只有 8 条 / 用户，没有总预算** | 群聊多人 × 多池时记忆块数量线性膨胀，且没有按 token 截断 |
| M6 | **注入块看不到时间与来源** | 模型不知道这条是「什么时候的事」、是否临近失效、出自哪句话；要判断只能再调 trace/search |
| M7 | **身份仍是不透明 id** | 块头是 `user_id`，正文常写「他」；虽然有「正在跟你说话的人」块，但对照成本还在 |
| M8 | **alias 重复注入** | 同一条 alias 既在记忆块又在说法对照块，浪费上下文 |
| M9 | **scope 割裂** | `pool` scope 的记忆换池就看不见；与「群里信息不带私聊」叠加后，跨池关系记忆容易被切断 |
| M10 | **老记忆无来源** | 索引功能之前的记忆 `source_seq` 为 NULL，trace 回不到原文，注入里也没有任何提示 |
| M11 | **群聊归属依赖 `lastUserId`** | 写入时默认取池里最后说话的人（`app/src/core/db.ts:632`），被记的人不是当前说话人时会挂错；目前靠正文带名字缓解，但结构化归属仍不可靠 |

## 三、可选方向

### A. 注入时机

- 改成**每轮都对当前说话人注入一次**，或至少在出现新未读时刷新该 `池|用户` 的缓存，而不是一次/会话。
- proactive tick 即使没有未读，也注入该池最近活跃用户的记忆。
- 保留 `seenPools` 只用于「近期上下文」，记忆注入独立计数，避免混用。

### B. 选择策略

- 优先级：当前说话人 > 本轮消息命中的 alias/关键词 > 置顶（可加 `pinned`）> 最近有效 > 其余。
- 上限从「固定条数」改为「token 预算 + 条数上限」双约束。
- 可选：注入一条「已过期但相关」的记忆并标注时间，避免模型误以为它仍有效。

### C. 展示

- 记忆块补 `from → to`（或「至今」）与来源提示，例如：
  `#12 [fact] 2026-10 起：他下个月搬家（来源 #45）`。
- 块头用显示名 + user_id：`记忆 张三（ou_xxx）`。
- alias 去重：进了说法对照就不再进记忆块，反之亦然。
- 对无来源的老记忆明确标注，或提供一次性的「按 created_at 附近消息回填来源」的可选迁移（需人工确认，别自动猜）。

### D. 写入归属

- 群里若被记的人不是当前说话人，`memory add` 显式传 `user`；正文带名字（已做）。
- 长期可考虑 `subject_user_id` / `subject_name` 快照，把「关于谁」和「谁说的」分开；但当前优先靠正文 + 来源消息。

### E. 可观测性

- 唤醒日志里记录本轮注入了哪个用户的几条记忆（id 列表），便于回答「她为什么没想起来」。
- Web 记忆页展示来源、有效区间，已做来源抽屉；可再补「未注入原因」排查。

## 四、待定

1. 注入频率：每轮 vs 一次/会话，token 成本与「她记得」之间的取舍。
2. 相关性怎么算：纯关键词、alias 命中，还是加 embedding / 置顶标记。
3. 预算按「每用户」还是「每池/每轮总量」。
4. 是否允许注入已过期记忆（带时间标注），还是坚持只给当前有效。
5. 老记忆来源要不要回填，回填的确认流程怎么走。
